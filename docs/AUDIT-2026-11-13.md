## 二、P0：真实缺陷（建议尽快改）

### P0-1 导入订阅没有总时间预算 → 大订阅必然超时
- 位置：`proxy/app.py:12362-12377`
- 事实：`Semaphore(8)` 并发 + 每源 `probe_source(timeout=8)`，候选上限 200。
  最坏耗时 ≈ 200 ÷ 8 × 8s = **200 秒**，而管理页请求走浏览器/网关（通常 60~120s 就断）。
- 现在的规模（69/87/135 站点）还没炸，是因为大部分源已入库被去重，真正探测的只有几十个。
  订阅一换大的、或首次导入，就会卡到超时，用户看到「导入失败」但源其实后台已经写了一半。
- 建议：给整轮探测加 **45 秒总预算**（`asyncio.wait(..., timeout=45)`），没跑完的写进
  「待探测」清单（`verified=False` 入库，交给巡检 25s 超时补判）。
- 对标：上游「导入订阅不阻塞管理页」的行为；做完后大订阅也不会卡死，源一个不丢。
- 值不值得：**值得，改动小（约 20 行）、风险低、直接消掉一个必然踩的坑。**

### P0-2 七个全局缓存放任增长（7×24 常驻进程的慢泄漏）
| 缓存 | 键域 | 现状 |
|---|---|---|
| `_MSEARCH_CACHE` | 搜索标题 | 读取时判 TTL，但**从不删除**，每搜一个新片名 +1 条 |
| `_MEDIA_REDIRECT` | 媒体 guid | 只写不删 |
| `_RESURRECT_FAIL` | 媒体键 | 只写不删（有 ts 但不清理） |
| `_XLIB_EP_MAP` | 小雅剧集 guid | 只写不删，每浏览一集 +1 |
| `_XLIB_MEDIA_MAP` | 小雅媒体 guid | 同上 |
| `_MAIN_SERVE_BG_FAILS` | 页面键 | 只增不减 |
| `_chart_resolved` / `_LOG_SAMPLE` | 榜单 guid / 日志采样键 | 键域天然有界，属观察项 |

- 影响：单条几十字节，十万条也才几 MB —— **不是立刻爆内存**，但小雅库 + 长时间使用会稳定爬升，
  且没有任何上限保护。NAS 上这是常驻进程，值得给护栏。
- 建议：统一加「上限 + 过期清理」（如 `_MSEARCH_CACHE` 2000 条 / 1h，
  `_XLIB_*` 按 5000 条 FIFO，`_MEDIA_REDIRECT`/`_RESURRECT_FAIL` 按 TTL 惰性清理）。
- 对标：上游没有这类缓存（我们独有）；做完后内存曲线变平，长期跑不掉速。
- 值不值得：**值得，一次性小改，属于「不做也不会马上坏、但永远不该缺」的护栏。**

## 三、P1：一致性/卫生问题（低成本，建议顺手清）

1. **版本号三处不一致**
   - `VERSION` = 1.2.2（准）、`pyproject.toml` = **1.1.0**、`proxy/build_info.py` 为构建期生成（正常）。
   - 后果：从 pyproject 读版本的工具有一天会误导人；发版审计时也不好看。
   - 做法：`pyproject` 改为 1.2.2，并在 build.sh 里同步校验两者（不一致就退出）。
   - 值不值得：**值得，1 分钟，纯元数据。**

2. **前端 `esc()` 定义了两次**
   - `admin_ui.py` 内联 JS 里 `function esc(...)` 出现在两处（早先分块拼接留下的），后者覆盖前者。
   - 目前两份实现相同，行为没错；但改一处不生效这种坑迟早踩。
   - 做法：删掉后一份，或改名并全量替换引用（删更稳）。
   - 值不值得：**值得，1 分钟。**

3. **203 处 `except Exception: pass`（app.py 占 104 处）**
   - 抽样看，多数是「缓存落盘失败/预热失败/标题旁路」这类**合理的防御**，不建议全面改（大面积改风险远大于收益）。
   - 但有 3 类会掩盖真故障，建议改成 `_log.debug`：
     1. 苹果CMS 解析/映射失败（会表现为「源没结果」但日志干净）；
     2. 播放地址解析/接线失败（表现为「点开没反应」）；
     3. 配置写入（`_persist` 类失败会让用户以为保存成功）。
   - 值不值得：**只改这 3 类的 5~8 处，值得；全量治理不值得。**

4. **`admin_token` 默认空 + 令牌有效期 0 天**
   - `config.py:323 admin_token=""`、`admin_auth.DEFAULT_MAX_AGE_DAYS = 0`（永不过期）。
   - 这是 2026-11-09 明确的设计决定（写接口不加上锁，避免把用户锁在门外），**不是 bug**；
     但建议在管理页「关于」里显式写一句「本机管理页无鉴权，请勿暴露到公网」，避免误判。
   - 值不值得：**只做文案提示，1 行；上锁不做。**

5. **模块级重复 import**（`app.py`：catalog×5、guard×21、json×10、os/time×3…）
   - 无功能影响（Python 幂等），是多次迭代堆积的痕迹；一次 ruff/pyflakes 清理即可。
   - 值不值得：**有空再做，纯卫生。**

## 五、设定合理性逐项核对

| 设定 | 值 | 判断 | 说明 |
|---|---|---|---|
| 单源探测超时 | 8s（外层 10s） | 合理 | 慢源会被判失败，但已由「巡检 25s + 多热词」兜住，不会误删 |
| 导入整轮预算 | **无** | **不合理** | 见 P0-1，建议 45s |
| 搜索等待上限 | 8.5s（聚合预算 6s） | 合理 | partial 兜底，超时不丢整批 |
| 海量库建库 | 单源 BUILD_BUDGET + HTTP 12s | 合理 | 一轮不会被一个死源拖死 |
| 分类表抓取超时 | 25s | 合理 | 后台任务，不进客户端等待路径 |
| 分页上限 `MAX_PAGES` | 250（×20 = 5000 条） | 偏大但合理 | 配合客户端无限滚动；`_GN_CATALOG_MAX_PG=40` 是另一套（原生热播墙），**语义不同，建议加注释防混用** |
| 广告过滤预算 | 6s | 合理 | 超时跳过，不阻塞起播 |
| 标题库/收藏/历史上限 | 4000/5000/500 | 合理 | 都有淘汰 |
| 管理令牌有效期 | 0（永不过期） | 需显式化 | 默认不开鉴权是既定决策，补一句风险提示即可 |

## 六、动作建议（按顺序，前两项是真收益）

1. **P0-1 导入总预算 45s**（约 20 行）：做完后任何规模的订阅都不会把管理页卡到超时，源不丢。
2. **P0-2 七个缓存加护栏**（约 40 行）：做完后 7×24 内存平稳。
3. **P1-1/P1-2 版本号 + 前端 esc 去重**（2 分钟）：纯一致性。
4. **P1-3 关键路径 5~8 处静默异常加日志**：下次「搜不到/点不开」时能自证原因。
5. P2 全部可选：`app.py` 拆两个函数、`xlib` 补 5 个用例 —— 属于长期投资，不影响当前功能。
